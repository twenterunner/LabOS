# LabOS REV 1.0.160 — QA Report

**Release:** LabOS REV 1.0.160  
**Schema:** 38  
**Baseline:** REV 1.0.159 rebuild  
**Scope:** Startup/data-schema compatibility repair.

## Root cause
REV 1.0.159 declared `ProtoLab.SCHEMA_VERSION = 37`, while users who had run the earlier Validation releases already had schema-38 IndexedDB state. The repository correctly rejects data whose schema is newer than the running application, so startup stopped with `This data was created by a newer schema.`

## Correction
- Runtime schema restored to **38**.
- Existing schema-38 state is accepted without downgrade or destructive rewriting.
- Explicit schema **37 → 38** migration added for REV 1.0.159 users.
- The bridge initialises Validation collections only when absent and preserves existing Prototype/Validation records.
- Service-worker deployment reset/version references moved to REV 1.0.160.

## Mandatory startup-compatibility regression
This failure mode is now a permanent release gate: future releases must be checked against populated browser state from the latest previously supported schema, not only against an empty/fresh database.

PASS — synthetic populated schema-38 state:
- schema 38 retained;
- Prototype request/route/equipment/Standard Test counts preserved;
- existing Validation programme and requirement records preserved.

PASS — populated REV 1.0.158 schema-38 demo state:
- Prototype requests: 24 → 24;
- Validation programmes: 19 → 19;
- Validation requirements: 81 → 81;
- bookings: 113 → 113;
- no `newer schema` rejection.

PASS — REV 1.0.159 schema-37 state:
- migrates to schema 38;
- Prototype request identity/order preserved;
- required Validation collections initialised if absent.
