Prototype and Validation — one LabOS operating model

REV 1.0.159 rebuilds Validation inside the same application runtime and UX framework used by Prototype. The two workstreams deliberately share the same portfolio conventions, programme cockpit, Programme Logic canvas, planning language, audit, reporting and archive semantics.

Validation → open programme. The workflow starts at Requirements: Requirements → Programme Logic → Resource Plan → Readiness → Execution → Verification → Report & Close.

  1. Define customer requirements manually or import the customer programme/specification.
  2. Review each requirement and its source clause, test leg, sequence/predecessor and DUT context.
  3. Review the proposed verification decision: Reuse, Adapt, Combine tests, Develop new or Other verification.
  4. Choose Generate Validation Programme only after the mapping has been reviewed. The Programme Logic graph is generated into controlled leg lanes rather than loose floating blocks.
  5. Use Resource Plan/Readiness/Execution exactly as the shared LabOS model intends, then close the RTM, report and lessons.

Validation → Requirements → Worked customer PDF example.

The example demonstrates four customer clauses split into Environmental durability and Mechanical durability legs. Archive Manager

Archive Manager.

Use the same archive workspace for Prototype builds and Validation programmes. Archive requires a reason and is audit retained. Restore is available where the current archive permissions permit it.

Management KPI dashboard

Management → KPI.

The KPI workspace is a period-aware operating-performance dashboard rather than a static scorecard. Use the sticky filter bar to combine period, lab/network, domain, Business Unit, product, programme, project, test/process family, equipment category and priority. Reset filters clears all KPI-only filters.

  1. Use the executive row for On-Time Delivery, Total Days Late, Right-First-Time, Median Lead Time, Cost vs Plan, Critical Capacity Load, Internal Network Capture and Outsourcing Avoided. Each headline KPI shows the selected-period value, target, movement versus the immediately preceding equivalent period and a sparkline; open a tile to see the underlying population.
  2. Requested date, accepted commitment, current forecast and actual completion are kept separate. Requested-date OTD therefore cannot be improved simply by moving commitments.
  3. Use Lost Programme Days by Cause, repeat/invalid-test cause Pareto, capacity bottlenecks and replanning analytics to understand why performance moved. Product failures that are valid test results are not counted as lab-caused invalid tests.
  4. Use Resource Allocation by Business Unit and the over-time stacked view to see where hours, cost, builds/cases and tests are consumed. Business Units come from controlled configuration, not free text.
  5. Use the network section to separate sister-lab capture from evidenced outsourcing avoidance. A sister-lab transfer counts as outsourcing avoided only when a documented external alternative/counterfactual exists.
  6. Cost metrics expose data coverage. Missing cost sources remain missing rather than being silently treated as zero or estimated. Development Cost stays blank until a controlled labour-cost source exists.
  7. Equipment and capability assurance separates selected-period performance from current status so historical filters do not misrepresent today’s overdue calibration/unavailable-equipment or skill risks.
  8. Prototype analytics are active now. Validation/DV/PV and Failure Analysis KPI definitions are already registered in the same framework, but their production values remain empty until those workflows create genuine source records.
  9. Open Configure targets to edit business targets. These targets are management settings and are not presented as universal IATF 16949 or ISO/IEC 17025 requirements.

Chart granularity is selected automatically from the chosen period (day, week, month or quarter), while long/empty periods retain readable axes and explicit empty-state behavior.

Understand the guided build editor

Prototype → open a build.

Follow yellow. Green means the controlled evidence for that stage/substep is complete. Exactly one yellow stage and one yellow action identify what must happen now. Grey is future/locked. A later stage cannot become actionable before the earlier controlled requirement is complete.

The sticky cockpit remains visible while you work and is the operational summary for the build: Build number, Requested delivery, Original commitment, Current commitment, Latest forecast, Build workflow, Substeps, Planning, Current stage & owner, Approvals, and Next step & owner.

Every process-step page follows the same order: Purpose → DO THIS NOW → Evidence progression → detailed work. The yellow action is executable, names its owner, and states what “done” means. When the underlying evidence is completed, the step turns green and LabOS moves yellow forward automatically. Approved evidence is not followed by a second mystery acknowledgement.

A-samples use Engineering need → Material → Process & methods → Controls → Plan & commit → Build readiness → Build & evidence → Verify & disposition → Handover & learn. B- and C-samples use the same path plus Formal release before Handover & learn.

The workflow provides IATF/ISO-oriented evidence support, not a certification claim. Controlled revisions, required approvals, competence, measurement-resource status, traceability, nonconformity control and objective evidence remain authoritative.

Create a prototype request: Control Plan and material timing

Requests → New prototype request → WHAT CONFIGURATION?

  1. Control Plan: LabOS offers controlled Control Plans tied to the same product only. Approved plans are preferred, but a same-product Draft or Approval requested plan may also be selected as the intended plan. It does not block route/resource planning merely because final approval is still pending. LabOS creates the approval as a later mandatory action and Build Readiness/execution cannot pass until the required approval is complete. A plan from another product is never selectable.
  2. Engineering supplied material: identify the supply owner and expected arrival at the lab. You may continue filling the Draft while this is incomplete, but the Draft cannot be submitted into the controlled workflow until both are known (unless exact material has already been issued).
  3. Known ETA does not mean material is physically ready. Once owner + ETA are known, route/control definition and planning may proceed. AUTO PLAN uses the ETA as the earliest material-available date. Build Readiness and execution remain blocked until the exact material is received and issued.
  4. Lab supplied material: the request can be submitted, but the Material stage must reserve exact matching stock or establish a dated incoming supply plan before Plan & commit can complete.
  5. If an existing Draft is missing engineering-supply timing, choose Edit request; the material planning basis fields are available there so the request cannot become a dead end.

Plan a prototype build

  1. Open Prototype → [build] → Material source & feasibility and confirm the exact BOM source/arrival/lot evidence.
  2. Open Route / method definition and confirm released processes/tests or controlled development.
  3. Open Resource plan & committed timing. Build the schedule manually or choose PREVIEW AUTO-PLAN. AUTO-PLAN is optional.
  4. LabOS plans around accepted lab closures, vacations, maintenance, calibration/training windows and existing bookings. Those are operating constraints, not items you must remove.
  5. If a true readiness gap exists, use the named action for the exact resource; for example, open the exact equipment evidence rather than a generic planning resolution.
  6. If the home lab still cannot produce a complete/acceptable plan, AUTO PLAN automatically adds a Network + external recovery section. It independently solves every active sister lab and shows the configured external facility timing/cost alternative rather than ending at “no planning option”. A sister-lab move requires the formal sender/receiver acceptance handshake; external execution requires an explicit governed scenario decision.
  7. When every required planning task has one valid booking, COMMIT CURRENT PLAN becomes available immediately. You can commit a deliberately non-optimal manual plan without running AUTO-PLAN first.

Control Plan / special approvals

Prototype → [build] → BUILD WORKFLOW → tile titled “Reuse approved controls…” / “Control Plan & special approvals”.

This tile appears only when the assurance profile requires the control step. Open the tile. LabOS lists only Control Plans for the same product. You may link an Approved plan or intentionally select a Draft / Approval-requested plan and approve it later. A pending final approval is carried visibly as controlled work rather than blocking planning unexpectedly. Choose Create & define Control Plan when no suitable plan exists. Link characteristics to route steps and define limits/specification, method/gauge, objective evidence and reaction plan. Required independent approval becomes a mandatory yellow/My Work action and must be complete before Build Readiness/execution.

Build readiness

Prototype → [build] → BUILD WORKFLOW → Build readiness.

Open the remaining readiness item. It should name the exact equipment, capability, skill or evidence and provide a direct next action. Accepted planning situations such as a closure or vacation must be planned around, not removed to make readiness green.

Execute / verify / release

  1. Build samples & capture process evidence: if the sample register is incomplete, the required sample count stays visible as the yellow prerequisite. Create the sample records, then use Sample / serial register to populate formal serials individually, generate a serial series, or import/export CSV while the permanent Lab Sample ID remains unchanged.
  2. Use Batch-fill parameters to populate a controlled sample parameter across blank cells or intentionally replace the batch. Use Evidence matrix and the process-step CSV import/export tools for larger parameter/result sets. Batch changes remain audit logged.
  3. Execute each route operation and record required process/Control Plan evidence. The yellow action follows the actual next incomplete operation/evidence requirement.
  4. Characterise, evaluate & disposition exceptions: record requested results; investigate and disposition any quality hold/nonconformity.
  5. Formal release approval: complete the configured release sign-off where required by the assurance profile.
  6. Deliver, retain records & feed learning: acknowledge delivery, retain records/lessons and close.

Sister-lab transfer

Planning → Lab Network Recovery or the sister-lab action from a build/task plan.

  1. The sending lab compares feasible sister labs and opens the candidate it wants to request.
  2. Before sending, review the visible decision facts: sample quantity, proposed start/finish, forecast, planned hours, equipment and assigned people. Expand the operation-plan foldout only when more detail is needed.
  3. Submit the formal transfer request with the sender rationale. No LIVE routing changes yet.
  4. At the receiving lab, open My Work or Planning → Lab Network Recovery → Transfer requests & acceptance. The receiver sees the same proposed sample/timing/resource evidence before deciding.
  5. Accept or reject with receiver rationale. Acceptance reruns the canonical planner against the receiver's current LIVE capacity, closures, people, equipment and readiness before routing changes.

Materials & Inventory corrections / scrap

Materials & Inventory → Edit / scrap… or Prototype → [build] → Material source & feasibility → Material quantity & disposition.

Received lot identity (part number, revision and lot/batch) is immutable. Authorised users may make controlled corrections without rewriting genealogy:

  1. Set / correct available quantity after a physical count.
  2. Add received / found quantity to the same controlled lot.
  3. Scrap / consume available quantity with mandatory reason and optional NCR/scrap-ticket/reference.
  4. Quarantine / release a lot and update location, expiry/retest date, supplier/source or receipt/certificate reference.
  5. For a build, Adjust reservation to increase/reduce/release exact-lot reserved quantity. For already issued material, Scrap / loss creates a separate disposition record and reduces usable issued quantity; it does not overwrite the issued genealogy.

Every adjustment records actor, timestamp, before/after quantity, reason and supporting reference in the transaction/audit history.

Audit Readiness

Governance → Audit Readiness.

Build audit population = completed/CLOSED builds only. Open nonconformities on in-progress builds remain in Operational watch and are not included in the audit score/report. Build-linked findings identify the build, deliverable, owner and record reference.

  1. Select the relevant IATF 16949 or ISO/IEC 17025 framework view.
  2. Review Internal audit section overview. Each row states the assessment, score and objective LabOS evidence used.
  3. Review the Relevant norm map. A Manual review row means no automated evidence rule is mapped; it is deliberately not shown as compliant.
  4. Prioritise Major findings, then Minor findings. Recommendations / opportunities for improvement are preventive and are not nonconformities.
  5. Use the Prototype build turtle to review inputs, resources, people, controls, outputs and measures around the app process flow.
  6. Choose Audit evidence pack → Print / save PDF for the printable evidence set.

The readiness percentage is a system-assisted internal indicator, not a certification score. Ready = 100%, Minor = 50%, Major = 0% at check level; risk weights are used for the overall readiness calculation. Unmapped norm sections remain manual review items.

Task replan history

Prototype → [build] → Resource plan & committed timing → Task replan history.

Each row shows the movement, task, From → To date, reason category and retained free-text rationale. This is separate from customer commitment history.

Resource Assurance

Resource Assurance in the left navigation.

Use Calibration, Maintenance and Training filters to locate the exact resource. A readiness call-up is a controlled planning event, not merely a reminder.

  1. Use Schedule calibration, Schedule maintenance or Schedule training for an individual call-up.
  2. Use Plan all due ≤30 d, ≤60 d or ≤90 d for a batch call-up. Overdue and unscheduled items inside the selected horizon are collected, then each item still goes through the collision/build-impact review before commit.
  3. A scheduled row shows Change schedule and Cancel schedule. Cancelling releases the reservation/capacity and removes the open scheduled-care action; the historical schedule and cancellation remain in the audit trail.
  4. Use Select visible → Review & schedule selected for an arbitrary batch.
  5. Retain the calibration certificate, maintenance evidence or training/competency certificate that closes the readiness requirement. A valid approved calibration interval should not trigger unnecessary recalibration.

Planning and execution use the canonical technical capability of each setup. Older saved equipment records that predate the dedicated planning-capability field are interpreted from their controlled equipment identity/scope, so a valid microscope/optical-inspection setup is not falsely reported as missing.

Reports

Open Reports or the build closeout step. Build Reports and the Audit Evidence Pack use the browser print dialog; choose Save as PDF when a portable copy is required.

Prototype route/method hand-off

Prototype → open build → Build Workflow → Reuse released route / work instructions

  1. If a method is incomplete, the fixed Next Step action names that exact operation and opens the correct correction path.
  2. Operations such as Surface Preparation that are intentionally manual/no-dedicated-equipment are not blocked for lacking a machine.
  3. If the current user is the Lab Planner, choose Switch to Process Engineer · …. The same build remains open and the exact Process Engineering action is shown immediately.
  4. After route/method confirmation, the workflow proceeds forward to Controls and then Planning; it should not bounce back unless the controlled definition actually changes.
  5. If a reused route/work instruction has a genuine build-specific delta, the fixed NEXT ACTION names the exact remaining reviewer (Process Engineer, then Quality/Product Safety where configured). Complete that named sign-off; LabOS does not hand the build to the Planner until the definition/control stage is actually complete. Orphaned stale approval records are reconciled automatically.

Laboratory scope & resource evidence

Lab Standards & Resources → Equipment & laboratory scope

The scope register lists every registered equipment asset and links capability/range/resolution with current readiness, calibration certificate/validity, maintenance due/history and the certified skills/people associated with released methods using that capability.

Build Report capability plots

Reports → open Build Report → SC / CC & classified characteristics

Capability/statistical detail is expanded by default. Numeric special/critical characteristics show the measured distribution, specification/target/mean markers, Cpk context where supported by the data, normality result, anomalies and coverage.

My Work action queue

Dashboard / My Work → Actions that require a decision or completion.

LabOS shows the entire mandatory queue assigned to the current user/role. Ordinary actions, approval/governance actions and scheduled readiness work are all included; the displayed cards are not truncated to an arbitrary top 10 or top 6. Improvement opportunities remain a separate foldout because they are opportunities rather than mandatory work.

Daily Operations load-balancing opportunities

My Work / Dashboard → Today’s improvement scan.

  1. Only opportunities LabOS can currently execute end-to-end are shown as actionable cards.
  2. Opening or accepting a card revalidates the exact booking, resource, qualification/readiness and conflict state against LIVE data.
  3. If the exact assignments changed, LabOS refreshes the proposal and asks you to review the current version before accepting.
  4. If the load is already back below the threshold, the card is removed and LabOS explains that no action is required.
  5. If the resource is still overloaded but an automatic same-lab rebalance is no longer complete, the card is retired from the executable queue and the user is guided to Planning. An outdated card must not end in an error-only withdrawal message.
