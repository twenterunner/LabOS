ProtoLab OS — User Manual REV 1.0.45

Task-based guide for the GitHub Pages proof-of-concept. The same guidance is available inside the application under Help & Manual.

Open application

Quick Start

Use the Demo role selector, open a request, then follow the single vertical checklist. The checklist is deliberately ordered so timing is generated only after material and process/test feasibility are understood.

  1. Request definition & submission
  2. Material source & feasibility
  3. Process route & test-method assessment
  4. Lab feasibility, resource plan & committed timing
  5. Control Plan, risk controls & special approvals
  6. Build readiness
  7. Identify units where required & execute the guided build
  8. Characterise, evaluate & disposition exceptions
  9. Release approval
  10. Deliver, retain records & feed learning
How engineering requests a prototype
  1. Choose New prototype request.
  2. Define product/configuration, quantity, objective, required date and requested characterisation.
  3. Choose only Engineering supplied or Lab supplied for material source.
  4. If Engineering supplied, give the supply owner and expected arrival at the lab.
  5. Submit. A forecast is intentionally not invented yet.
How material feasibility works

Engineering supplied: the expected arrival date is a planning constraint; the exact physical lot must later be received and issued before Build Readiness.

Lab supplied: the planner can reserve only an exact part-number/revision match with enough quantity. Reservation makes the material planning-eligible; issue to the build is still required before execution.

How Process Engineering prepares a request for planning
  1. Open Process route & test-method assessment.
  2. Confirm/change the actual build route.
  3. For each step, use a released standard process or start controlled modified/new-process development.
  4. Ensure standard setup/cycle time, equipment capability and required competency exist.
  5. Map requested characterisation to a released Standard Test. If no standard matches, define development hours, provisional execution time, equipment capability and required skill.
How lab timing is determined

AUTO-PLAN can always generate a best-feasible preview after submission. If material or process/test definition is incomplete, the forecast is explicitly provisional and uses controlled assumptions. Formal timing commitment still requires those inputs to be complete.

For defined work, the optimizer searches every capable machine and every person associated with the required skill, works around build/readiness bookings, inserts calibration/maintenance/training recovery where appropriate, and searches later working slots rather than failing on normal conflicts. The only structural hard-stop is when the lab has no equipment capability at all or no person associated with a required skill.

Standard times are owned by the lab. For a product with previous builds, the planner blends the standard with the median same-product actual duration. New/modified methods use an explicit Process Engineer development allowance.

How to use the visual swimlane planner
  1. Open Visual Resource Planning.
  2. Use Overall for the portfolio, Per build for one request, Per equipment for machine loading or Per person for people/qualification loading.
  3. Choose the planning horizon.
  4. Toggle Show potential projects to overlay probability-weighted pipeline scenarios. Dashed pipeline bars are not committed bookings.
  5. Use OPTIMIZE PORTFOLIO to rebuild the earliest best-feasible active schedule in priority/due-date order.

Calibration, maintenance and training actions appear on the same visual timeline because they consume real capacity.

How the Lab Manager maintains planning master data
  1. Open Lab standards, tests & skills.
  2. Review/edit standard-process setup time, cycle time, batch/unit basis, equipment capability and competency.
  3. Review/edit released Standard Test setup/cycle time, equipment capability and competency.
  4. Maintain which lab people are qualified for each competency.
How to create and approve a Control Plan
  1. Open Control Plan, risk controls & special approvals.
  2. For each special characteristic define a target and/or objective limits, method/gauge, reaction plan and required evidence.
  3. The Quality owner cannot approve their own revision when separation of duties is enabled.
  4. Use the independent Approver / Reviewer. Product-safety-relevant builds also create an actionable Product Safety approval.
How to perform Build Readiness

Build Readiness checks the physical build conditions, not just planning assumptions: exact material issued, confirmed/released processes and test methods, approved Control Plan, calibrated planned equipment, qualified people, risk controls and applicable approvals. Every blocker explains why, owner, required action and evidence.

How a technician executes a build
  1. Generate/confirm serials.
  2. Start a controlled build step; the app records operator, timestamp, revision and equipment context.
  3. Enter required evidence/measurements.
  4. Complete the step. Actual elapsed duration is retained for the future learning model.
How characterisation, deviations and rework work

Record raw results manually or by CSV. Objective limits are evaluated automatically. Failed results remain linked to the serial, process/build, method, equipment/calibration, operator and timestamp. A deviation/rework path keeps the release hold until disposition and verification are complete.

How the system learns from completed builds

Closing a delivered build captures actual process durations, first-pass yield, scrap, rework, recurring issues and lessons learned. Historical same-product records are visible in the planning screen and refine future duration estimates. The POC seeds historical data so this behaviour is visible immediately.

How to find evidence and create a report

Use global search for request ID, product, serial, process, lot or deviation. Generate a Prototype Build Report from Reports/request records. Drafts are labelled AUTO-GENERATED · NOT APPROVED; approved report records retain approver, role and timestamp.

Compliance intent

This POC supports IATF 16949-aligned control concepts. Certification, customer-specific requirements, approved procedures, validated signatures and enterprise record governance remain organisation responsibilities.

REV 1.0.23 · Samples, process execution and result linkage

The build flow is now explicit: requested quantity → sample register → route execution → in-process Control Plan measurements → end characterisation → genealogy.

Lab Sample ID is the permanent system trace key. Sample number is the editable human-facing label. Formal serial number is separate and is mandatory for V/P but optional for E0/E1.

Equipment is selected for each process execution and must have the required capability; it is not assigned permanently to a sample. Control Plan data is recorded during the linked process step. End-characterisation data is recorded later against the same sample register, manually or by CSV.
